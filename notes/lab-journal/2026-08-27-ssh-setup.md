## Lab

AWS Lightsail SSH Custom Port Setup

## Phase

BLACKFORGE Phase X — Infrastructure & SSH

## Objective

Set up a secure SSH connection from my Kali Linux machine to an AWS Lightsail Ubuntu server and move SSH from the default port **22** to a custom port **2244**.

The final goal was to connect using:

```bash
ssh server1
```

instead of manually specifying the IP, port, and private key every time.

## 2. Checked the SSH configuration file

I initially tried:

```bash
~/.ssh/config
```

This produced:

```text
permission denied
```

### Why?

I was accidentally trying to **execute** the configuration file as a command.

The correct way to read it was:

```bash
cat ~/.ssh/config
```

The existing configuration contained:

```text
Host server1
    HostName 13.212.27.162
    User ubuntu
    Port 2244
    IdentityFile ~/.ssh/LightsailDefaultKey-ap-southeast-1.pem
```

This showed that an SSH shortcut already existed, but the server had not yet been configured to use port 2244.

### Lesson

`~/.ssh/config` is a configuration file, not a command.

---

## 3. Prepared the `.pem` key

I checked the contents of:

```bash
ls -la ~/.ssh
```

The Lightsail private key already existed in the directory.

The key had restrictive permissions:

```text
-r-------- ... LightsailDefaultKey-ap-southeast-1.pem
```

For a standard SSH private-key permission setup, I used:

```bash
chmod 600 ~/.ssh/LightsailDefaultKey-ap-southeast-1.pem
```

This ensures the private key is not readable by other users.

# 4. Configured the Lightsail Firewall

In AWS Lightsail, I added a custom firewall rule:

```text

```

I kept TCP 22 enabled temporarily.

At this point:

```text

```

The reason for keeping port 22 was to maintain a recovery path while testing 2244.

# 6. Discovered systemd Socket Activation

I investigated why port 2244 was not listening.

I ran:

```bash
sudo systemctl status ssh.socket --no-pager
```

This showed:

```text
TriggeredBy: ssh.service
Listen: 0.0.0.0:22
        [::]:22
```

This revealed that **systemd socket activation** was controlling the listening sockets.

I also checked:

```bash
sudo systemctl cat ssh.socket
```

This showed the SSH socket configuration.

### Important discovery

On this Ubuntu installation, SSH involved:

```text
sshd_config
+
ssh.socket
+
sshd-socket-generator
```

Therefore, simply changing `sshd_config` did not guarantee that the socket itself would listen on the new port.

```text

[::]:2244
```


As a result:


```text

```

The Lightsail browser SSH connection also stopped working.

Because this was a **fresh lab server with no important data**, I deleted the instance and recreated it.

### Lesson

This was an important operational lesson:

> Never remove or break the existing SSH access until the replacement connection has been successfully tested.

# 10. Configured the systemd SSH Socket

I created a systemd socket override:

```bash
sudo systemctl edit ssh.socket
```

The configuration initially used:

```ini
[Socket]
ListenStream=
ListenStream=22
ListenStream=2244
```

After investigation, I discovered the Ubuntu installation was generating SSH socket configuration automatically.

The important generated configuration contained IPv4 listeners:

```text
ListenStream=0.0.0.0:2244
ListenStream=[::]:2244
ListenStream=0.0.0.0:22
ListenStream=[::]:22
```

I removed the unnecessary manual override and allowed the generated configuration to handle the socket.

Then:

```bash
sudo systemctl daemon-reload
```

and:

```bash
sudo systemctl restart ssh.socket
```

# Problems Encountered

## Problem 1 — Permission denied copying `.pem`

### Error

```text
cp: cannot create regular file ... Permission denied
```

### Investigation

```bash
ls -ld ~/.ssh
ls -la ~/.ssh
```

The `.ssh` directory belonged to my user, and the `.pem` file already existed.

### Lesson

Check the destination before assuming a directory-permission problem.

---

## Problem 2 — Tried to execute `~/.ssh/config`

### Error

```text
zsh: permission denied: /home/umesh/.ssh/config
```

### Cause

The configuration file was treated as a command.

### Solution

Read it using:

```bash
cat ~/.ssh/config
```

### Lesson

Configuration files need to be read or edited, not executed.

---

## Problem 3 — `Connection refused` on port 2244

### Error

```text
ssh: connect to host SERVER_IP port 2244: Connection refused
```

### Cause

The SSH client was trying to use 2244, but the server was not correctly listening on IPv4 port 2244.

### Investigation

```bash
sudo ss -tlnp | grep ssh
```

### Lesson

A firewall rule alone does not make a service listen on a port.

---

## Problem 4 — SSH socket activation

### Problem

Changing:

```text
/etc/ssh/sshd_config
```

did not immediately produce the expected listener.

### Cause

The Ubuntu server was using:

```text
ssh.socket
```

and:

```text
sshd-socket-generator
```

### Lesson

Always investigate how a service is managed before modifying its configuration.

---

## Problem 5 — Lost SSH access

During the first attempt, incorrect socket configuration caused both remote access methods to fail.

### Result

The server had to be recreated.

### Lesson

The most important recovery rule learned:

```text
Keep old connection
       ↓
Configure new connection
       ↓
Test new connection
       ↓
Confirm new connection
       ↓
Remove old connection
```

## Problem 6 — Accidentally deleted HTTP 80

While modifying the Lightsail firewall, I accidentally removed the HTTP rule.

I added it back:

```text

```

### Lesson

After modifying firewall rules, always review the entire firewall configuration instead of assuming only the intended rule changed.

# What I Learned

### SSH

I learned how to configure SSH on a remote Ubuntu server and change it from the default port 22 to a custom port.

### SSH Client vs SSH Server

The client configuration on Kali:

```text
~/.ssh/config
```

is different from the server configuration:

```text
/etc/ssh/sshd_config
```

Both sides need to agree on the connection parameters.

### SSH Keys

I learned how `.pem` private keys are used for AWS SSH authentication and why private-key permissions matter.

### SSH Config Shortcuts

I learned that one:

```text
~/.ssh/config
```

file can contain configurations for multiple servers.

### Linux Networking

I learned to use:

```bash
ss -tlnp
```

to determine which ports are actually listening.

### systemd

I learned that modern Ubuntu systems may use:

```text
ssh.socket
```

for SSH socket activation.

### Cloud Firewalls

I learned that AWS Lightsail's firewall is separate from the service running inside Ubuntu.

For SSH to work:

```text
Kali
 ↓
Lightsail Firewall
 ↓
Ubuntu listening port
 ↓
sshd
```

must all be correctly configured.

# Security Lessons

Changing SSH from port 22 to 2244 is **not a replacement for proper SSH security**.

It can reduce noise from basic automated scans, but attackers can discover non-standard ports.

More important security controls include:

* Use SSH keys instead of passwords.
* Protect private keys.
* Use restrictive private-key permissions.
* Disable unnecessary authentication methods.
* Disable unnecessary services.
* Keep the operating system updated.
* Restrict firewall access where practical.
* Monitor SSH authentication logs.
* Use least privilege.
* Avoid exposing unnecessary ports.

For this lab, the Lightsail firewall currently allows SSH from any IPv4 address. A future hardening step would be restricting TCP 2244 to a trusted source IP where practical.

---

# Key Takeaways

1. **Never change remote SSH access without keeping a recovery path.**
2. **A firewall rule does not mean a service is listening.**
3. **`ss` shows what is actually listening.**
4. **`sshd_config` controls SSH server configuration.**
5. **`~/.ssh/config` controls client-side SSH shortcuts.**
6. **systemd socket activation can affect how SSH ports are configured.**
7. **Test the new SSH port before removing the old one.**
8. **Document failures because they reveal how the system actually works.**
